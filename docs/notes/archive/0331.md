### 2. 主链路收口判断

基于 3 月 31 日这轮整理和验证，这组问题当前可以视为“基本收口”，但仍有两个明确边界：

#### 已基本收口的部分

- 浏览器和 APP 的网关主链路逻辑已经基本打通
- APP 初始化接口不会再误跳到浏览器申请页 HTML
- APP 登录未授权时能返回可消费的 JSON 并自动创建申请
- APP 已授权时，网关会把请求正确转发到上游
- 后台 APP 凭据页面的误导性文案已修正
- 根路径资源 / 根路径接口路由逻辑已补齐
- 首次访问和每请求热路径已做第一轮性能优化

#### 仍然保留的边界

1. `j.kuaipu.com.cn:2027` 当前动态路径大量返回 `302 -> /Resource/Html/error.htm`  
   这会影响“真实业务成功返回”的最终联调判断。

2. legacy managed proxy 仍然不具备原生 WebSocket 代理能力  
   这意味着消息推送如果强依赖 WebSocket，则需要：
   - `IIS ARR + URL Rewrite`
   - 或升级到 `.NET 10` 版本网关

### 3. 当前建议

当前不建议继续在这一组问题里无边界深挖，更合理的状态是：

- 内部记为：主链路基本收口
- 对外口径：网关侧未再发现新的逻辑性阻塞，剩余异常主要来自上游体验站状态，以及 legacy 架构中 WebSocket 的能力边界

## 三、今天形成的工程结论

### 1. 关于浏览器主链路

当前浏览器主链路里的网关侧逻辑问题，已没有明显新增阻塞。  
如果后续仍有异常，需要优先区分：

- 是否是上游站点自身返回错误页
- 是否是体验站当前状态不稳定

而不是默认继续怀疑网关路径改写。

### 2. 关于官方 APP

当前项目里“APP 相关功能”的真实主线已经明确：

- 不是让第三方 APP 来适配一套新协议
- 而是让现有官方 APP 也能走统一认证网关

因此后续所有 APP 相关问题，都应围绕下面四层判断：

1. 初始化接口是否正确
2. 登录接口是否正确
3. 登录后 `token / SessionKey / ashx / WCFService` 是否正确
4. 清缓存 / 清数据 / 卸载重装后，设备授权是否重新触发

### 3. 关于消息推送

当前阶段可以内部认定：

- WebSocket：legacy managed proxy 不支持
- SSE / 长轮询：可以部分支撑
- 如果老板后面把“消息推送必须完整可用”列为强验收项，就需要单独拉出来处理，不应混在一般路径修复里继续零散推进

### 4. 关于性能

当前已经有初步共识：

- 低到中等并发下，当前 legacy 网关可接受
- 最可能先成为瓶颈的是 SQLite 写锁和热路径上的每请求写操作
- 如果老板后续重点追问并发性能，应优先考虑：
  - 让代理层交给 IIS ARR
  - 网关自己尽量只做认证、授权、审计，不把高频热路径都压在 SQLite 写操作上

### 3. 每个改动解决了什么

1. `isAppLikePath` 加入 `isBootstrapPath`  
   解决了 `sys.ashx` 某些非标准 action（例如 `checkupdate`）被漏识别的问题。

2. `postJson` 根级字段提取  
   解决了 APP 把 `MachineId / DeviceImei / TrAppKey` 等字段放在 `postJson` 根级时，设备标识完全丢失的问题。

3. raw JSON body 解析  
   解决了 APP 以 `application/json` 提交登录时，身份字段无法识别的问题。

4. 去掉过早依赖 `IsLegacyApp`  
   让根地址模式下的站点解析不再依赖“先识别出 legacy APP”，而是路径命中即可路由。

5. 扩展路径匹配 + 根站点回退  
   任意 `.ashx / .svc / /default.aspx` 路径都更容易被正确路由到上游，而不会落入网关 HTML。

6. `LooksLikeMobileAppRequest` 二次检测  
   当设备暂时走浏览器路径，但请求看起来明显是移动端接口请求时，仍返回 JSON 而不是 HTML 重定向。

## 六、4 个真实缺陷的修复与封板判断

### 1. 这轮修复的文件

- `src/GatewayDemo.Legacy.Web/Infrastructure/ProxyRequestModule.cs`
- `src/GatewayDemo.Legacy.Web/Infrastructure/DeviceCredentialService.cs`
- `src/GatewayDemo.Legacy.Web/Infrastructure/LegacyGatewayRepository.cs`

### 2. 每个缺陷的修复摘要

#### 缺陷 1：`sys.ashx` 无 `action` 返回 HTML

修复方式：

- 在 `ProxyRequestModule.cs` 的 `TryHandleLegacyAppCompatibilityRequest` 中增加 `string.IsNullOrWhiteSpace(action)` 分支
- 对该场景返回 `text/plain` 版本号，而不是 HTML

结果：

- 现在返回 `6.26.0`
- 不再误回 HTML

#### 缺陷 2：`text/plain` 包 JSON body 无法提取设备标识

修复方式：

- 在 `DeviceCredentialService.cs` 的 `ParsePostJson` 中增加对 `text/plain` 的识别
- 当 body 以 `{` 开头时，尝试按 JSON 解析并提取设备字段

结果：

- 现在能命中设备标识提取逻辑
- 返回 JSON 403，而不是 HTML

#### 缺陷 3：根路径 `/` + `okhttp` UA 返回 HTML

修复方式：

- 在 `ProxyRequestModule.cs` 中，当 `TryResolveSite` 失败后，增加 `HasMobileAppUserAgent` 检查
- 命中时返回轻量 JSON：`{"Status":1,"GatewayReady":true}`

结果：

- `okhttp` 根路径请求不再返回 HTML
- 浏览器主链路仍保持 HTML，不受影响

#### 缺陷 4：`Guid.Parse` 对非 GUID ID 抛 500

修复方式：

- 在 `LegacyGatewayRepository.cs` 的 `MapAuthorization` 中将 `Guid.Parse` 改为 `Guid.TryParse`
- 解析失败时回退到 `Guid.Empty`

结果：

- 不再抛异常
- 数据异常时请求仍能被可控处理
