## 2. 问题 1 —— 撤销设备后无法正常弹窗

### 2.1 研发原始现象

> 关于我之前修复的「重复撤销响应未清空 GatewayMessage；只携带设备号、不携带旧 SessionKey 时，未识别为已撤销设备；原生 APP UA 携带已撤销 HMAC 凭据时，错误进入旧弹窗格式」，**现在撤销设备会没办法正常弹窗**。

### 2.4 根因链（四层）

**① `LegacyGatewayRepository.cs:3283-3294` —— 撤销时物理删除 HMAC 凭据行**

```csharp
var appCredential = GetAppCredential(connection, transaction, authorization.DeviceId);
if (appCredential != null)
{
    DeleteReplayNonces(connection, transaction, appCredential.CredentialKey);
    command.CommandText = "DELETE FROM GatewayAppCredentials WHERE DeviceId = @DeviceId;";
    command.ExecuteNonQuery();
}
```

表结构（见 1.7）没有 `IsActive` / `RevokedAtUtc`，**无法表达"已撤销但仍可识别归属"**，只能删行。

**② `DeviceCredentialService.cs:705 ResolveSignedAppContext` —— 查不到凭据即抛"尚未登记"**

`GetAppCredentialByKey` 返回 null → 抛 `DeviceCredentialException("APP 设备尚未登记。", 401)`。
执行流**根本走不到** `ProxyRequestModule.cs:617` 的 `device.RequiresReview` / 撤销判定。

**③ `ProxyRequestModule.cs:539` —— catch 分支优先级把弹窗分支挤掉（真正的元凶）**

```csharp
catch (DeviceCredentialException ex)
{
    ...
    if (hasAppCredentialHeaders)            // ← :539 优先级最高，且硬编码文案、丢弃 ex.Message
    {
        WriteApiCredentialError(context, ex.StatusCode, "gateway_app_auth_failed", "接口鉴权失败。");
    }
    else if (descriptor.IsLegacyApp)        // ← :547 真正能弹窗的分支，永远轮不到

    }

```

`WriteApiCredentialError`（`:1764`）的响应体只有三个字段：

```csharp

    "{\"error\":\"" + HttpUtility.JavaScriptStringEncode(errorCode ?? string.Empty)
    + "\",\"message\":\"" + HttpUtility.JavaScriptStringEncode(message ?? string.Empty)
    + "\",\"requestId\":\"" + HttpUtility.JavaScriptStringEncode(requestId) + "\"}");
```

**④ `DeviceCredentialService.cs:2067/2076 HasAppCredentialHeaders` 判定过宽（OR 逻辑）**

```csharp
private static bool HasAnyAppHeaders(HttpRequest request)
{
    return ...
        || !string.IsNullOrWhiteSpace(request.Headers[AppTimestampHeaderName])
        || !string.IsNullOrWhiteSpace(request.Headers[AppNonceHeaderName])
        || !string.IsNullOrWhiteSpace(request.Headers[AppBodyHashHeaderName])
        || !string.IsNullOrWhiteSpace(request.Headers[AppSignatureHeaderName]);

```

5 个头**任一非空**即判为"接口客户端"，于是原生 APP 只要带 HMAC 头就一律走 ③ 的第一分支。

**附带缺陷**：部分路径下 `Company` 字段被填成入口地址 `http://127.0.0.1:26100` 而非企业名 `KUAIPU`。

### 2.5 修改方案

> 三步做完才算彻底修复。**只做第 1 步**能让弹窗立刻回来（文案是"尚未登记"），**做完 2、3 步**文案才是准确的"授权已撤销"。

#### 步骤 1（必做，最小改动）—— 修 catch 分支优先级与文案丢弃

`ProxyRequestModule.cs:536-560`，把"是否原生 APP"作为第一判据，`hasAppCredentialHeaders` 降为次级，并**不再丢弃 `ex.Message`**：

```csharp
// 修改后
var isNativeApp = descriptor.IsLegacyApp
    || (MobileClientDetector.IsNativeAppRequest(context.Request,
            LegacyAppCompatibilityPolicy.GetProfile(site))
        && !MobileClientDetector.IsBrowserDocumentNavigation(context.Request));

if (isNativeApp)
{
    // 原生 APP（含带 HMAC 头的）一律走完整弹窗 JSON，携带 ex.Message
    LegacyAppResponseWriter.WriteBlockedJson(context, ex.StatusCode, ex.Message, descriptor);
}
else if (hasAppCredentialHeaders
         || ShouldRequireAppAuthentication(context, site, requestPath, credentialService))
{
    // 纯接口客户端（服务端对服务端）保持精简 JSON，但把真实原因带出去
    WriteApiCredentialError(context, ex.StatusCode, "gateway_app_auth_failed", ex.Message);
}
else
{
    WriteHtmlPage(context, ex.StatusCode, runtime.Renderer.RenderDeviceCredentialErrorPage(ex.Message));
}
```

⚠️ 注意 `WriteBlockedJson` 会把 HTTP 状态改写成 200 + `X-Gateway-Original-Status`，这与通道 A/B 行为一致，APP 侧解析逻辑不用改。

⚠️ 若担心纯接口客户端拿到中文文案，可在 `WriteApiCredentialError` 里保留 `errorCode` 机器可读、`message` 用 `ex.Message`——这正是上面的写法。

#### 步骤 2（推荐）—— 让撤销后的 HMAC 凭据仍可识别

**2a. 加列**（`GatewayDatabaseInitializer.cs`）：

```csharp
// :16 —— 版本号 10 → 11
internal const int CurrentSchemaVersion = 11;

// 在 :537-583 的 EnsureColumn 序列末尾追加
EnsureColumn(connection, transaction, "GatewayAppCredentials", "RevokedAtUtc", "TEXT NULL");
EnsureColumn(connection, transaction, "GatewayAppCredentials", "RevokedReason", "TEXT NULL");
```

同时在建表 DDL（`CREATE TABLE GatewayAppCredentials`）里补上同名列，保证新库/老库一致。

**2b. 撤销改为软删**（`LegacyGatewayRepository.cs:3283-3294`）：

```csharp
var appCredential = GetAppCredential(connection, transaction, authorization.DeviceId);
if (appCredential != null)
{
    DeleteReplayNonces(connection, transaction, appCredential.CredentialKey);   // nonce 仍然清掉
    command.CommandText = @"
UPDATE GatewayAppCredentials
SET RevokedAtUtc = @Now, RevokedReason = 'authorization-revoked'
WHERE DeviceId = @DeviceId;";
    command.Parameters.Clear();
    command.Parameters.AddWithValue("@Now", ToDbDateTime(now));
    command.Parameters.AddWithValue("@DeviceId", authorization.DeviceId);
    command.ExecuteNonQuery();
}
```

**2c. 重新签发时清撤销位**：`issue-app-credential` 路径的 `INSERT OR REPLACE` 需显式写 `RevokedAtUtc = NULL`，否则重新签发后仍被判为已撤销。

**2d. 解析时区分两种失败**（`DeviceCredentialService.cs:705 ResolveSignedAppContext`）：

```csharp
var credential = repository.GetAppCredentialByKey(key);
if (credential == null)
{
    throw new DeviceCredentialException("APP 设备尚未登记。", 401);
}
if (credential.RevokedAtUtc.HasValue)
{
    // 关键：让上层能识别"撤销"，而不是"不存在"
    throw new DeviceCredentialException(
        "移动 APP 设备授权已撤销，请重新申请授权；审批通过后请重新登录。", 403);
}
```

⚠️ **安全性**：软删后必须保证撤销的凭据**不能**通过签名校验放行。上面在 `GetAppCredentialByKey` 之后立即拦截，签名验证之前/之后都可以，但不能漏。同时 `GatewayManagedDevices.HasAppCredential = 0` 的更新（`:3253`）保持不变。

**2e. 老库清理**：升级到 schema 11 时，历史上被 DELETE 掉的凭据无法恢复，这些设备重新签发凭据即可。

#### 步骤 3（推荐）—— 修 `Company` 字段污染

#### ② 模型加属性

#### ③ 读取映射

#### ④ 写入（`LegacyGatewayRepository.cs:3303 TouchAuthorizationAsync`）

```csharp
public Task TouchAuthorizationAsync(string deviceId, string clientIp, string siteKey,
                                     string requestPath,          // ← 新增
                                     CancellationToken cancellationToken)
{
    var now = DateTime.UtcNow;
    var heartbeatKey = "authorization:" + deviceId + ":" + siteKey;
    if (!TryReserveHeartbeat(heartbeatKey, now)) { return Task.CompletedTask; }

    QueueBestEffortHeartbeatWrite(heartbeatKey, now,
        "LegacyGatewayRepository.AuthorizationHeartbeat",
        "deviceId=" + deviceId + "; siteKey=" + siteKey,
        delegate
        {

UPDATE GatewayDeviceAuthorizations
SET LastSeenIp = @LastSeenIp, LastSeenSiteKey = @LastSeenSiteKey,
    LastSeenPath = @LastSeenPath, LastSeenAtUtc = @LastSeenAtUtc
WHERE DeviceId = @DeviceId AND Status = @Status;";
                command.Parameters.AddWithValue("@LastSeenPath", (object)safePath ?? DBNull.Value);
                ...
            }
        });

}
```


### 4.5 根因（三点，均超出研发原描述）

**① `BusyTimeout` / `CommandTimeout` 都不是墙钟上界**

`LegacyGatewayRepository.cs:3555 ExecuteDatabaseWrite<T>`：

```csharp
var started = Stopwatch.StartNew();
var cumulativeWait = TimeSpan.Zero;
SQLiteException lastLockException = null;
for (var attempt = 1; ; attempt++)
{
    try
    {
        T result; long databaseCallMilliseconds;
        lock (DatabaseWriteSyncRoot)                    // ← 进程内全局串行化
        {
            var databaseCall = Stopwatch.StartNew();    // ← ⚠️ 计时器在拿到锁之后才启动
            result = action();
            databaseCallMilliseconds = databaseCall.ElapsedMilliseconds;
        }
        ...
        return result;
    }
    catch (SQLiteException ex)
    {
        if (!IsDatabaseLocked(ex) || attempt >= DatabaseWriteRetryCount) { ...; throw; }
        lastLockException = ex;
        var retryDelay = GetRetryDelay(attempt);
        cumulativeWait += retryDelay;
        Thread.Sleep(retryDelay);      // ← ⚠️ 重试后 busy_timeout 重新计时 ⇒ 无墙钟上界
    }
}
```

`DatabaseWriteRetryCount = 5`，`GetRetryDelay(attempt) = min(50 × attempt², 1000) ms`（`:3649`）。
最坏情况：5 次尝试 × 每次最多 15 s busy_timeout + 退避 ≈ **75 s 以上**，请求线程全程阻塞。

**② `databaseCallMs` 系统性低估**

计时器在 `lock` **之后**才启动，**不含锁外排队时间**。
实测中 3 个并发浏览器都等了 12 秒，日志里却只落了 1 条 `DatabaseWriteSlow` —— 另外两个的等待时间被计成 0，连阈值都没触发。**这会让线上排查完全看不见真实等待。**

**③ IIS 重叠回收会让进程内锁失效**

`DatabaseWriteSyncRoot` 是 `private static readonly object`，只在**单个 w3wp 进程内**有效。
IIS `disallowOverlappingRotation` 出厂默认 `false` ⇒ 回收时新旧 w3wp 并存 ⇒ 两个进程各自持有一把锁，SQLite 层面直接撞车。

实测：临时把该项改回 `false`，抓到双 w3wp 并存，816 次导航中**回收窗口内的耗时 p50 从 282 ms 涨到 1814 ms**（48 次 ≥ 1000 ms，0 次失败）。
（`setup-demo-sites.ps1:1008` 已设为 `true`，**测试后已恢复**。）

### 4.6 修改方案

#### ① 给 `ExecuteDatabaseWrite` 加跨重试的墙钟上界（最关键）

`LegacyGatewayRepository.cs:3555`：

```csharp
private const int DatabaseWriteWallClockBudgetMilliseconds = 2000;   // 新增常量，建议 2 s

private static T ExecuteDatabaseWrite<T>(Func<T> action, string operationName = null)
{
    var started = Stopwatch.StartNew();
    ...
    for (var attempt = 1; ; attempt++)
    {
        try { ... }
        catch (SQLiteException ex)
        {
            var budgetExhausted = started.ElapsedMilliseconds >= DatabaseWriteWallClockBudgetMilliseconds;
            if (!IsDatabaseLocked(ex) || attempt >= DatabaseWriteRetryCount || budgetExhausted)
            {
                if (IsDatabaseLocked(ex))
                {
                    GatewayErrorLogger.LogException(HttpContext.Current,
                        "LegacyGatewayRepository.DatabaseWriteLockExhausted", ex,
                        "operation=" + operationName
                        + "; attempts=" + attempt
                        + "; budgetExhausted=" + budgetExhausted
                        + "; elapsedMs=" + started.ElapsedMilliseconds);
                }
                throw;
            }
            ...
        }
    }
}
```

⚠️ 同时需要**收紧 `BusyTimeout`**：单次 15 s 的 busy_timeout 会让第一次尝试就吃掉全部预算。
建议把请求线程路径上的连接改用较短的 busy_timeout（如 500 ms），把 15 s 留给后台/管理台路径。
见 `SQLiteConnectionConfigurator.cs` 与 `BusyTimeoutMilliseconds` / `BestEffortBusyTimeoutMilliseconds`（当前 15000 / 50）。

⚠️ **超时后的降级策略要按调用点区分**：
- 心跳、审计（`RecordAuditAsync`）等 → 丢弃即可，不能影响业务请求
- `CreateBrowserManagedDevice` 等**必须成功**的写 → 不能丢，只能让它抛，并给用户一个明确的"系统繁忙，请重试"页面，**不要**静默 500

#### ② 修 `databaseCallMs` 低估

把慢写日志的判据从 `databaseCallMilliseconds` 改为 `started.ElapsedMilliseconds`（含锁等待），
并**同时输出两个值**，便于区分"锁等待慢"和"SQLite 本身慢"：

```csharp
var totalMilliseconds = started.ElapsedMilliseconds;
if (lastLockException != null) { ...LockRecovered... }
else if (totalMilliseconds >= SlowDatabaseWriteLogThresholdMilliseconds)
{
    GatewayErrorLogger.LogDiagnostic(HttpContext.Current,
        "LegacyGatewayRepository.DatabaseWriteSlow",
        "outcome=succeeded; operation=" + operationName
        + "; attempts=" + attempt
        + "; cumulativeWaitMs=" + (long)cumulativeWait.TotalMilliseconds
        + "; lockWaitMs=" + (totalMilliseconds - databaseCallMilliseconds)   // ← 新增
        + "; databaseCallMs=" + databaseCallMilliseconds
        + "; elapsedMs=" + totalMilliseconds);
}
```

#### ③ 把残留的请求线程同步写迁到异步路径

`RecordAuditAsync`（`:3342`）是最容易迁的 —— 审计日志丢一条不影响正确性，
直接改走 `QueueBestEffortHeartbeatWrite` 同款的 `ThreadPool` + `Monitor.TryEnter` 模式。

`CreateBrowserManagedDevice`（`:1416`）**不能异步化**（后续逻辑立刻要用返回的设备），
但可以：把该写操作从"每次匿名请求都建设备"收敛为"只在真正需要落库时建"（配合问题 6 的修改，
原生 APP 请求不再进这条路径后，这里的调用量会大幅下降）。

#### ④ 部署硬性前置

把 `disallowOverlappingRotation:true` 写进部署文档与安装脚本的**校验步骤**（不只是设置，还要在启动自检里读回确认），发现为 `false` 时在管理台首页打醒目告警。

#### ⑤（可选）压测回归

```powershell

node .\pw-issue3-sustained.js   # 持续

```

### 6.1 研发原始现象

```

```
另一张截图显示实际生效值：`单次超时: 请求/响应头=100000 ms | 读写=100000 ms`

### 6.2 版本差异

当前包 1.0.34.0 的校验消息**已经改过**（`GatewayPathRuleOptions.cs:71-84`）：

```csharp

}
```

研发看到的是 1.0.28.0 的旧消息。**但根因没修，只是把异常换成了静默的错误解释。**

### 6.3 根因 —— 用 `> 86400` 猜单位

`GatewayPathRuleOptions.cs:98-120 ResolveTimeoutMilliseconds`：

```csharp
if (configuredMilliseconds > 0) { return configuredMilliseconds; }
if (configuredLegacyValue <= 0) { return fallbackMilliseconds; }
if (configuredLegacyValue > 86400) { return configuredLegacyValue; }   // ← :113 当毫秒
// 否则 × 1000 当秒
```

后果 —— **同一份配置文件里相邻两条规则语义不同**：

| 配置写法 | 实际生效 | 是否符合意图 |
|---|---|---|
| `TimeoutSeconds: 5000`（本意 5000 ms） | 5,000,000 ms = **83 分钟** | ❌ 灾难性 |
| `TimeoutSeconds: 100000`（本意 100000 ms） | 100,000 ms | ✅ 碰巧对 |
| `TimeoutSeconds: 30`（本意 30 s） | 30,000 ms | ✅ 对 |

即：**5000 和 100000 这两个值，一个被当秒、一个被当毫秒**，运维完全无法预测。

另有互斥校验（`:38-39` 调用、`:45-55` 逻辑）：同时设置 `TimeoutSeconds` 与 `TimeoutMilliseconds` 直接抛
`"Gateway path rule cannot set both TimeoutSeconds and TimeoutMilliseconds."`

### 6.4 修改方案

**核心原则：单位由属性名决定，绝不猜。**

#### ① 删掉启发式（`GatewayPathRuleOptions.cs:98-120`）

```csharp
private static int ResolveTimeoutMilliseconds(
    int configuredMilliseconds, int configuredLegacyValue, int fallbackMilliseconds)
{
    if (configuredMilliseconds > 0) { return configuredMilliseconds; }
    if (configuredLegacyValue <= 0) { return fallbackMilliseconds; }
    return checked(configuredLegacyValue * 1000);   // *Seconds 一律按秒，不再看 86400
}
```

#### ② 校验收回到真正的秒范围（`:71-84`）

```csharp
private static int ValidateLegacyTimeoutValue(int value, string propertyName)
{
    if (value < 0 || value > 86400)
    {
        throw new InvalidOperationException(
            "Gateway path rule " + propertyName + " 的单位是秒，取值必须为 0 或 1~86400。"
            + "若要配置毫秒，请改用 " + propertyName.Replace("Seconds", "Milliseconds") + "。"
            + " 当前配置值：" + value);
    }
    return value;
}
```

⚠️ **这是破坏性变更**：线上若真有 `TimeoutSeconds: 100000` 这类配置，升级后会启动失败。

#### ③ 兼容过渡期（强烈建议，与 ② 二选一或叠加）

保留旧值可加载，但**必须显式告警**，并给运维一个季度的迁移窗口：

```csharp
private static int ValidateLegacyTimeoutValue(int value, string propertyName)
{
    if (value < 0 || value > 86400000)
    {
        throw new InvalidOperationException(/* 同上 */);
    }
    if (value > 86400)
    {
        // 兼容历史站点文件，但把这次"猜"记录成显式告警
        GatewayErrorLogger.LogDiagnostic(null,
            "GatewayPathRuleOptions.LegacyTimeoutUnitAssumed",
            "property=" + propertyName + "; configuredValue=" + value
            + "; interpretedAs=milliseconds; action=请改用 "
            + propertyName.Replace("Seconds", "Milliseconds"));

    return value;
}
```

同时在**管理台的站点配置页**把两个值都显示出来：

```

```

这样运维一眼能看出"我写的值被怎么解释了" —— 研发那张截图的困惑正来源于此。

#### ④ 文档与示例配置

站点配置模板里把 `TimeoutMilliseconds` 作为**推荐写法**，`TimeoutSeconds` 标注为「已废弃，仅为兼容历史配置保留」。

### 8.4 根因（精确到行）

**① `ManagedReverseProxy.cs:1542-1572 WriteRequestBody` 全程无 try/catch**

```csharp

private const int MaxLegacyAppLoginCaptureBytes = 1024 * 1024;

    if (!context.Request.InputStream.CanRead) { return; }   // ← :1552 首次触碰 InputStream

    var contentLength = context.Request.ContentLength;
    if (contentLength > MaxRequestBodyBytes)

    if (context.Request.InputStream.CanSeek) { context.Request.InputStream.Position = 0; }

    using (var upstreamStream = request.GetRequestStream())
    { context.Request.InputStream.CopyTo(upstreamStream); }

```

`:1552` 与研发堆栈 `WriteRequestBody → get_InputStream → GetEntireRawContent` **完全对上**。

**② `ManagedReverseProxy.cs:558-574 IsClientDisconnectAbort` 覆盖缺口**

```csharp

    { return false; }          // ← 只认 WebException + RequestCanceled
```

⇒ 客户端断开在这条路径上被当成**服务器错误**记进错误日志、并可能回 500，而不是静默的
`ClientDisconnected` 诊断。这就是研发看到满屏 `已中止 I/O 操作` 的原因。

（对照：`:530-556 IsUpstreamTimeout` 会遍历整条 `InnerException` 链，做法是对的；
`:576-590 BuildTransportDiagnosticDetail` 输出 `upstream/transportStatus/socketError/socketNativeError/timeoutMilliseconds/readWriteTimeoutMilliseconds/keepAlive/connectionLimit/retryAttempted/retryOutcome`。）

### 8.5 修改方案

#### ① 给 `WriteRequestBody` 加保护（`ManagedReverseProxy.cs:1542`）

```csharp
private static void WriteRequestBody(HttpContext context, HttpWebRequest request)
{
    if (!POST && !PUT && !PATCH && !DELETE) { return; }

    Stream inputStream;
    try
    {
        inputStream = context.Request.InputStream;     // ← 真正会抛的地方
        if (!inputStream.CanRead) { return; }
    }
    catch (System.Web.HttpException ex) when (IsClientAbortHResult(ex))
    {
        throw new GatewayClientDisconnectedException("客户端在上传请求体时中断连接。", ex);
    }
    catch (System.Runtime.InteropServices.COMException ex) when (IsClientAbortHResult(ex))
    {
        throw new GatewayClientDisconnectedException("客户端在上传请求体时中断连接。", ex);
    }

    var contentLength = context.Request.ContentLength;
    if (contentLength > MaxRequestBodyBytes)
    { throw new System.Web.HttpException(413, "Request body exceeds maximum allowed size."); }

    if (inputStream.CanSeek) { inputStream.Position = 0; }

    try
    {
        using (var upstreamStream = request.GetRequestStream())
        { inputStream.CopyTo(upstreamStream); }        // ← CopyTo 中途也可能断
    }
    catch (System.Web.HttpException ex) when (IsClientAbortHResult(ex))
    {
        throw new GatewayClientDisconnectedException("客户端在上传请求体时中断连接。", ex);
    }
    catch (IOException ex) when (IsClientAbortHResult(ex))
    {
        throw new GatewayClientDisconnectedException("客户端在上传请求体时中断连接。", ex);
    }
}
```

新增自定义异常类型（放在 `ManagedReverseProxy.cs` 同目录，或复用现有异常体系）：

```csharp
internal sealed class GatewayClientDisconnectedException : Exception
{
    public GatewayClientDisconnectedException(string message, Exception inner)
        : base(message, inner) { }
}
```

#### ② 扩展 `IsClientDisconnectAbort`（`ManagedReverseProxy.cs:558`）

```csharp
// ERROR_OPERATION_ABORTED     = 0x800703E3  由于线程退出或应用程序请求，已中止 I/O 操作
// ERROR_NETNAME_DELETED       = 0x80070040  指定的网络名不再可用
// ERROR_CONNECTION_ABORTED    = 0x800704D4
private static readonly int[] ClientAbortHResults =
{ unchecked((int)0x800703E3), unchecked((int)0x80070040), unchecked((int)0x800704D4) };

private static bool IsClientAbortHResult(Exception exception)
{
    for (var current = exception; current != null; current = current.InnerException)
    {
        if (Array.IndexOf(ClientAbortHResults, current.HResult) >= 0) { return true; }

        var socketException = current as SocketException;
        if (socketException != null
            && (socketException.SocketErrorCode == SocketError.ConnectionReset
                || socketException.SocketErrorCode == SocketError.ConnectionAborted
                || socketException.SocketErrorCode == SocketError.Shutdown))
        { return true; }
    }
    return false;
}

private static bool IsClientDisconnectAbort(HttpContext context, Exception exception)
{
    if (exception is GatewayClientDisconnectedException) { return true; }

    // 保留原有判定
    var webException = exception as WebException;
    if (webException != null && webException.Status == WebExceptionStatus.RequestCanceled)
    {
        try { return context == null || context.Response == null || !context.Response.IsClientConnected; }
        catch (System.Web.HttpException) { return true; }
    }

    // 新增：按 HResult / SocketError 遍历 InnerException 链
    if (IsClientAbortHResult(exception))
    {
        try { return context == null || context.Response == null || !context.Response.IsClientConnected; }
        catch (System.Web.HttpException) { return true; }
    }
    return false;
}
```

⚠️ **不要**无条件把所有 `HttpException` 当客户端断开 —— 必须靠 HResult 精确匹配，
否则会把真正的服务端错误也吞掉。

#### ③ 客户端断开走静默路径

`ProxyRequestModule.HandleRequest` / `ManagedReverseProxy.Proxy` 的顶层 catch 里，
`IsClientDisconnectAbort` 为真时：
- 记 `GatewayErrorLogger.LogDiagnostic(..., "ManagedReverseProxy.ClientDisconnected", ...)`（**不是** `LogException`）
- **不要**尝试写响应（客户端已经走了，写响应会二次抛异常）
- 直接 `context.ApplicationInstance.CompleteRequest()`

这与当前 `ClientDisconnected` 分支的行为一致，只是让入口覆盖到 `HttpException` / `COMException`。

```powershell
.\repro-io-abort3.ps1
# 期望：13 次中断全部记为 ClientDisconnected 诊断，错误日志里 0 条 HttpException/COMException
```

### 9.4 定性：**这是刻意设计，不是 bug**

`ProxyRequestModule.cs:757-763`（原始英文注释）：

```csharp
// A recovery cookie can identify a revoked legacy APP device even when the client
// keeps sending the SessionKey that revocation deleted. It may drive the review
// flow above, but an approved device must obtain a new upstream login session;
// otherwise reapproval would accidentally revive the old bearer credential.
var isSessionOnlyRevokedLogin = legacyDescriptor.IsRevokedSessionKey
    && legacyDescriptor.IsLoginRequest
    && string.IsNullOrWhiteSpace(legacyDescriptor.UserId);
```

**设计意图明确**：重新批准后**不能**让旧 bearer 凭据复活，必须重新登录换新 session。这是正确的安全决策。

支撑机制 —— `LegacyGatewayRepository.cs:3256-3281 RevokeAuthorizationAsync`：

```csharp
command.CommandText = @"
DELETE FROM GatewayRevokedLegacyAppSessions WHERE ExpiresAtUtc <= @Now;
INSERT OR REPLACE INTO GatewayRevokedLegacyAppSessions (SessionKeyHash, DeviceId, RevokedAtUtc, ExpiresAtUtc)
SELECT SessionKeyHash, DeviceId, @Now, @ExpiresAtUtc FROM GatewayLegacyAppSessions WHERE DeviceId = @DeviceId;
DELETE FROM GatewayLegacyAppSessions WHERE DeviceId = @DeviceId;
DELETE FROM GatewayBrowserRecoveryTokens WHERE DeviceId = @DeviceId;
DELETE FROM GatewayBrowserCredentials WHERE DeviceId = @DeviceId;";
command.Parameters.AddWithValue("@ExpiresAtUtc",
    ToDbDateTime(now.AddDays(Math.Max(90, configuration.Gateway.DeviceCookieLifetimeDays))));
```

### 9.5 三个可改进点

#### ① 重新批准时清理撤销表（**推荐修**）

撤销时 SessionKey 进 `GatewayRevokedLegacyAppSessions`，保留 `max(90, DeviceCookieLifetimeDays)` 天；
**重新批准时没有清理这张表** ⇒ `IsRevokedSessionKey` 长期为 `true`
⇒ 只要 APP 不清本地缓存，就会一直收到 401，用户体验上像"永久坏掉"。

在批准流程（`ApproveAuthorizationAsync` / `ApproveRequestAsync` 一类方法）里补：

```csharp
command.CommandText = "DELETE FROM GatewayRevokedLegacyAppSessions WHERE DeviceId = @DeviceId;";
command.Parameters.AddWithValue("@DeviceId", deviceId);
command.ExecuteNonQuery();
```

⚠️ **安全性权衡**：清掉之后，若 APP 仍持有旧 SessionKey，它会被当作有效 session 放行。
判断依据是"旧 session 在上游是否还有效" —— 由于撤销时 `GatewayLegacyAppSessions` 已被删，
网关本地无记录，请求会被当新 session 转发给上游，上游若已过期自然会拒。
**若上游 session 长期有效，则不应清理**，此时改用改进点 ③ 的方案。
**请与研发确认上游 session 生命周期后再决定是否落这一条。**

#### ② 修 `Company` 字段污染（与问题 1 步骤 3 同一处）

`Company` 被填成入口地址 `http://127.0.0.1:26100` 而非企业名。

#### ③ 状态码语义（**需 APP 侧配合**）

响应 HTTP 状态是 **200**（真实状态在 `X-Gateway-Original-Status: 401`）。
只看 HTTP 状态码的 APP 会认为"登录成功"，然后拿着空 token 继续请求 → **死循环**。

三个选项：

| 方案 | 做法 | 代价 |
|---|---|---|
| A（推荐） | APP 侧改为读 `body.LoginStatus` / `GatewayBlocked` / `ReloginRequired` | 需要 APP 发版 |
| B | 网关加站点级开关 `ReturnRealStatusForLegacyApp`，开启后直接回 401 | 老 APP 可能把 401 当网络错误 |
| C | 保持 200，但在 `Msg` 里加显式引导文案（如"请退出后重新登录"） | 治标 |

**建议 A + C 并行**：网关侧先把文案做足，同时推动 APP 改判据。

⚠️ 注意 `LegacyAppResponseWriter.WriteBlockedJson` 一律回 200 是**全局约定**（问题 1 的通道 A/B 也是），
若改成 B 方案，必须整体评估，不能只改 session_expired 这一条路径。
