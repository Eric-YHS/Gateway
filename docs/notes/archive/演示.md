# 统一认证网关 DEMO 演示脚本

## 使用方式

这份稿子按“双机模式”写：

- 演示电脑：只负责操作浏览器和终端
- 提词电脑：打开这份文档，照着“操作 + 台词”往下讲

建议总时长控制在 **7 到 9 分钟**。

## 当前口径

后续这份讲稿默认按 [需求边界说明.md](./需求边界说明.md) 执行：

- 主需求：给现有官方 APP 套网关
- 次需求：浏览器和 APP 都走统一认证
- 非当前主需求：开放给第三方 APP 的自定义接入协议

也就是说，演示时不要再把“自定义 `AppKey / Secret` 页面”讲成 APP 主需求本身；那一块现在只作为可选增强项保留。

## 正式演示脚本

### 1. 开场定位

**操作**

1. 窗口 A 打开：`http://localhost:5050/gateway`
2. 画面停留 5 秒。

**台词**

“这次演示的不是在 ERP 里额外加一个验证页，而是在 ERP 前面增加一层独立的统一认证网关。所有访问先进入网关，再由网关判断当前设备是否允许访问目标站点，通过之后，请求才会被反向代理转发到后端 ERP 或其他业务站点，所以 ERP 本体基本不用改动。”

“这套能力本质上是前置访问控制，它更适合作为独立层存在。这样做有四个直接好处：第一，ERP 本体尽量零改动，实施风险最低；第二，一个网关就能同时保护 ERP、WMS、财务等多个站点；第三，访问控制逻辑和业务逻辑解耦，后续升级不会牵动 ERP；第四，公网只暴露网关，安全边界更清楚。”

“技术栈上，这版 Demo 用的是 .NET 10 + ASP.NET Core，反向代理用微软官方 YARP，数据层用 EF Core。Demo 阶段先用 SQLite 跑通，正式部署可以直接切到 SQL Server，所以和现有微软体系衔接最顺。”

### 2. 先证明后台不暴露在公网

**操作**

1. 在窗口 A 地址栏输入：`http://localhost:5050/admin/login`
2. 等页面显示 404。
3. 然后切回：`http://localhost:5050/proxy/erp-main/portal`

**台词**

“首先这个公网入口并不暴露管理后台，外部用户从业务入口进来，只能看到网关，不会直接看到后台登录页。这个 Demo 里，管理后台只挂在独立管理端口上，公网业务端口不会提供 `/admin/login` 这类入口，所以外部扫描也看不到后台表面。”

“我的设计是管理后台一定要独立端口，而不是藏在某个路径下。因为隐藏路径只是降低可见度，不是真正减少攻击面。独立管理端口意味着业务口根本不挂后台页面，再配合防火墙、宿主机绑定或堡垒机，就能把管理流量和业务流量彻底分开。”

### 3. 演示未授权设备拦整站

**操作**

1. 在窗口 A 访问：`http://localhost:5050/proxy/erp-main/portal`
2. 等系统自动跳到网关页。
3. 指给总裁看：
   - 当前设备号
   - 目标站点
   - 当前状态
   - 申请表单
   - 站点选项

**台词**

“这里不是只拦登录页，而是直接拦整个站点。受保护的访问路径统一走 `/proxy/{siteKey}/...`，所以不管访问的是门户页、报表页还是接口，只要设备没有放行，都会先被网关接住。网关会先识别当前设备上下文，如果没有有效授权，就把请求重定向回申请入口，而不是把请求直接打到 ERP 上。”

“浏览器场景下，这里会先读取网关签发的浏览器设备令牌，同时结合浏览器请求头生成环境信号；APP 场景下则是读取签名请求头，走另一套校验链路。所以浏览器和 APP 是两条接入链路，但统一归到同一个网关体系里管理。”

“我们的主策略是设备校验为主、IP 为辅，所以客户换公网 IP、用花生壳、内网穿透甚至部分 VPN，都不会直接破坏已授权设备的访问体验。IP 更多是审计和风控参考，不是唯一凭据。”

“如果客户前面还有 IIS、SLB、WAF 或 Nginx，这个网关也能处理真实客户端 IP。它只会信任配置里的可信代理地址或 CIDR 段，不会无条件相信 `X-Forwarded-For`，所以不会被客户端自己伪造转发头带偏。”

### 4. 提交接入申请

**操作**

1. 在网关页填写：
   - 公司名称：`华东制造集团`
   - 申请人：`王工`
   - 联系电话：`13800000000`
   - 申请原因：`演示新设备接入`
2. 勾选站点：
   - `ERP 主站`
   - `WMS 东仓`
3. 点击“提交接入申请”。
4. 等页面回到网关页，状态显示“等待审批”。

**台词**

“这一步模拟的是客户新设备首次接入。当前这版 Demo 里，申请和审批数据先落在网关自己的存储里，后面如果方案确认，再和 ERP 现有流程做接口对接。也就是说，网关现在已经把设备号、申请人、联系电话、目标站点、目标路径这些信息完整收集起来了，后续接 ERP 接口时，主要是把这里的申请数据往外推送，而不是重做一套流程。”

“如果同一台设备连续提交多次申请，也不会把数据搞乱。当前逻辑里，如果这台设备已经有一条待审批申请，新提交会更新原申请，而不是不断新增待审批单。所以申请记录和当前有效授权是分开管理的，不会越跑越乱。”

### 5. 后台审批

**操作**

1. 切到窗口 B：`http://localhost:5051/admin/login`
2. 输入账号密码登录。
3. 在待审批申请卡片里展示：
   - 设备号
   - 申请人
   - 访问 IP
   - 目标站点
4. 备注填写：`演示环境临时放行`
5. 保留 `ERP 主站` 和 `WMS 东仓` 两个勾选。
6. 点击“批准并放行”。

**台词**

“管理面被单独放在管理端口，不再和公网业务入口混在一起。管理员看到的是待审批设备、已放行设备和审计日志，不需要进入 ERP 本体做改造。这里的审批动作本质上是在网关里生成一条设备授权记录，并把允许访问的站点 Key 一起绑定进去，所以它不是简单改页面状态，而是直接改变后续代理放行逻辑。”

“后台登录本身也做了收口，使用用户名加密码哈希，不再用共享 PIN，并且登录接口有限流，避免管理口被暴力尝试。”

“如果这台设备后续再次审批，系统会把新批准的站点权限合并进去，而不是生成多条并行生效的授权。所以它天然支持一个设备一次认证、多站点管理。”

### 6. 证明主站即时放行

**操作**

1. 切回窗口 A。
2. 再次打开：`http://localhost:5050/proxy/erp-main/portal`
3. 展示业务页面已打开。
4. 指一下页面里的：
   - `ERP 主站 / 业务入口`
   - `X-Gateway-Site`
   - 页面说明文字

**台词**

“审批通过后，放行立即生效。这里看到的已经不是网关的静态页，而是后端业务站点真实返回的页面，说明反向代理已经打通了。也就是说，设备授权一旦生效，网关会允许这台设备继续访问对应站点，然后由 YARP 把请求真正转发给上游业务系统。”

“这里还能看到 `X-Gateway-Site`，说明网关在转发时会把站点身份带给上游。同时代理路径上的 `/proxy/erp-main` 这样的前缀，对后端是透明处理的，后端拿到的仍然是它原来的业务路径。所以 ERP 后端不需要知道网关细节，也不需要做特殊适配。”

“如果有人乱拼一个不存在的站点 Key，网关会直接返回 404；如果站点存在但这台设备没授权，对应请求会被带回 `/gateway`。所以站点 Key 不只是路由标识，也是授权判断的一部分。”

### 7. 演示多站点统一认证

**操作**

1. 仍在窗口 A，点击页面里的 `WMS 东仓`，或者直接输入：

```text
http://localhost:5050/proxy/wms-east/portal
```

2. 展示 `WMS 东仓 / 业务入口` 已直接打开。

**台词**

“这一步演示的是一个客户部署多个站点时，同一设备一次审批后可以跨站访问，不需要每个站点都重复走一遍认证流程。底层做法不是复制多份授权，而是在同一个设备授权记录下面挂多个站点权限，所以统一认证和多站点管理是合在一起的。”

“新增一个站点也不需要改代码，只要在配置里新增站点 Key、显示名称、描述和上游地址，网关启动时就会自动生成对应的代理路由。这意味着后续扩 ERP 子站、WMS、财务、OA 都很顺。”

### 8. 演示站点级权限控制

**操作**

1. 在窗口 A 打开：

```text
http://localhost:5050/proxy/finance/portal
```

2. 展示页面再次被带回网关。

**台词**

“统一认证不等于全站全放开。虽然是同一设备，但放行范围仍然可以精确到站点粒度。刚才没批准财务站点，所以这里仍然会被拦住。也就是说，网关在放行前不仅会判断这台设备有没有授权，还会继续判断这条授权里是否包含当前访问的站点 Key，这样才能做到统一认证下的细粒度控制。”

“这一步其实是在提前回答一个管理问题：统一认证解决的是统一入口和统一设备身份，不是取消权限边界。权限边界仍然可以做到按站点、按角色继续细分。”

### 9. 展示审计日志

**操作**

1. 切回窗口 B。
2. 重点展示：
   - 已授权设备
   - 最近审计日志
3. 如果日志里能看到，依次指出：
   - 申请提交
   - 审批通过
   - 放行访问
   - 站点被拦截

**台词**

“后台除了审批，还能看到设备授权结果和完整审计轨迹。包括谁申请、谁被批准、访问了哪个站点、哪些请求被放行、哪些请求被拦截，后续都可以继续接到企业自己的审计体系里。现在审计里已经会记录设备号、站点、客户端 IP、操作类型和时间点，所以后面无论是接日志平台还是做异常告警，基础数据已经具备了。”

“也就是说，这里不仅能回答‘能不能进’，还能回答‘是谁进的、什么时候进的、进了哪个站点、是被放行还是被拦截’。这也是为什么后面要接告警平台、日志平台会比较顺。”

### 10. 说明 APP 接入边界

**操作**

1. 画面停在后台首页，或者停在体验站登录页。
2. 如果现场有真机，可补一句“官方 APP 也只改服务器地址，仍然先走网关”。
3. 不把“签发 APP 密钥”页面作为主线演示动作。

**台词**

“这里要澄清一下 APP 的需求边界。当前主需求不是让客户再理解一套新的 APP 协议，也不是要求官方 APP 之外的新 APP 来配合网关，而是让现有官方 APP 在尽量不改原运行机制的前提下，也能先经过这层网关。” 

“也就是说，APP 这条线现在真正要做的是：现有官方 APP 只改服务器地址或站点入口，然后它原来的初始化、登录、SessionKey、WCF 和 ashx 这些链路继续正常工作，再统一归到同一套申请、审批、授权和审计体系里。”

“后台里现在保留的 `AppKey / Secret` 这一页，可以理解成一个可选增强项。后面如果要给第三方 APP 或新开发的 APP 提供开放式接入协议，可以继续用；但它不是我们当前第一优先级的验收主线。” 

### 11. 结尾收口

**操作**

1. 画面停在后台首页，或者停在体验站登录页再切回后台首页。
2. 用 30 到 40 秒做总结。

**台词**

“这版 Demo 已经把核心闭环跑通了。现在可以做到独立网关前置、整站访问控制、多站点统一认证、审批后即时放行、管理端口隔离，并且已经把浏览器和现有官方 APP 统一纳入同一套网关思路里。也就是说，网关这一层已经具备独立成站、独立部署、独立存储和独立管理的能力。”

“部署上，它既可以跑在 Windows，也可以容器化部署。推荐形态是公网或 DMZ 只暴露网关，ERP 后端继续留在内网。Demo 里已经按这个思路把网关和后端做了网络隔离。”

“持久化上，只要业务数据库和相关密钥材料保留，容器重建、服务重启后，已审批的设备记录不会整体失效；如果后续启用自定义 APP 密钥模式，对应凭据也能继续保持。所以这套方案不是演示态的一次性状态机，而是可以走向正式部署的。”

“性能和高可用上，YARP 这一层主要做的是设备识别、授权判断和代理转发，真正重的业务处理仍然在后端系统。后续如果产品化，可以继续往多实例、负载均衡、共享数据库和共享 key ring 的方向扩展。”

“下一步如果方案确认，再继续对接原 ERP 的申请审核接口、短信和微信等多因子能力，以及多管理员分权、配置界面、通知机制和正式上线前的安全加固。”

## 可选附加段：展示浏览器环境变化会触发重新审批

这段不是必须，但如果你想把“设备校验不是只认一个 Cookie”讲得更扎实，可以在第二版视频里加上。

### 附加段操作

1. 在已经放行的公网窗口打开开发者工具。
2. 切到 `Network conditions`。
3. 取消默认 User-Agent，改成另一个浏览器标识。
4. 再次访问：`http://localhost:5050/proxy/erp-main/portal`

### 附加段台词

“系统不是只认一个本地凭据，还会同时校验浏览器环境信号。这个信号是根据浏览器请求头组合出来的摘要，不是单纯认一个 Cookie。环境变化后，设备会进入待复核状态，避免凭据被简单复制后长期滥用。这样做的目的，是把‘设备凭据存在’和‘当前访问环境是否还是原来的环境’两件事分开判断。”

“当前 Demo 版本里，如果浏览器把设备 Cookie 清掉，系统会把它当成新的浏览器设备，所以需要重新提申请。后面如果要进一步优化这类恢复体验，可以再叠加短信确认或设备恢复机制。”
