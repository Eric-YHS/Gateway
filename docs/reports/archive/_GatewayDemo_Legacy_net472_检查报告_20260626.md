## 二、问题 3 详细复现与根因

### 2.1 复现步骤

1. 用移动 APP 请求 `/proxy/2027/user/login`，POST body 包含：
   ```json
   {
     "Action": "Login",
     "UserId": "dubx",
     "UserName": "杜同学",
     "CompanyId": "3093683",
     "DataCenterId": "001",
     "DeviceImei": "330666A2FBA34F138885B8C76B9A6781"
   }
   ```
   结果：生成待审核申请 `3093683 / DEV-260626-4CD8FF`，申请人“杜同学”。

2. 用同一 IMEI 访问 `/proxy/2027/BillForm/DoAccountSetConfig?isApp=1&DataCenterId=001&LocaleId=2052&device_imei=330666A2FBA34F138885B8C76B9A6781`。
   结果：又生成一条新的待审核申请 `001 / DEV-260626-F887E4`，申请人“移动APP”，企业名称“001”。

### 2.2 根因分析

1. `DeviceCredentialService.BuildLegacyAppIdentitySources` 使用每次请求中可变的身份字段组合（companyId + userId + dataCenterId + deviceImei 等）计算 `IdentityHash`。当后续请求缺少 `UserId`/`CompanyId` 时，生成的 `IdentityHash` 与 `/user/login` 请求完全不同，系统因此认为是一台新设备，进而可能创建新的待审核申请。

2. `AutoCreateLegacyAppRequest` 在更新已有待审核申请时，直接把 `descriptor.ApplicantName`、`descriptor.CompanyName` 等字段传给了 `CreateOrUpdateRequestAsync`；而 repository 中的 `CoalescePreserve` 只要新值非空就会覆盖旧值，导致后续不完整请求把姓名、企业号等覆盖为“移动APP”、“001”等默认值。

### 2.3 修复内容

本次修复涉及两个文件：

- **`DeviceCredentialService.BuildLegacyAppIdentitySources`**：调整身份源优先级，优先使用 `DeviceImei`、`MachineId`、`AppKey`、`DeviceNo` 等稳定硬件/应用标识生成 `IdentityHash`，避免同一设备因请求携带字段不同而被识别为新设备。

- **`ProxyRequestModule.AutoCreateLegacyAppRequest`**：新增 `PreserveMoreCompleteIdentity` 合并逻辑。在更新已有待审核申请前，对 `CompanyName`、`ApplicantName`、`Phone` 等字段按以下规则合并：
  - 若旧值为空，采用新值；
  - 若新值为空，保留旧值；
  - 若新值是默认回退值（如 applicant 回退“移动APP”），保留旧值；
  - 若旧值长度大于新值，认为旧值信息更丰富，保留旧值；
  - 其余情况采用新值。

- **`ProxyRequestModule.AutoCreateLegacyAppRequest`**：对 `Reason` 字段也做了保留处理，已有完整原因时仅追加当前请求摘要，不会被覆盖；同时限制总长度不超过 2000 字符，避免同一设备被反复拦截时原因字段无限增长。
