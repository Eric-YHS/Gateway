# 兼容版重构待确认

## 已确认约束

以下内容已按老板回复锁定，不再作为可选项：

1. 开发环境必须兼容 **Visual Studio 2019**
2. 目标框架必须兼容 **ASP.NET + .NET Framework 4.7.2**
3. 网关站点相对独立，**不要求页面与原系统保持同构**
4. 接口层允许采用 **Web API2**，且贵司当前也在使用 Web API
5. 部署环境要兼容 **Windows Server 2008 R2 + IIS 7.5**
6. 反向代理可以直接采用 **IIS ARR + URL Rewrite** 这类成熟组件，不再强求全部代码自研
7. 网关部署在客户现有服务器上，网关自有库允许直接使用 **SQLite**
8. 内网环境**不能联网**，但允许使用**离线依赖包**；若引入第三方，要注意版权问题
9. APP 接入方式要**不影响原有 APP 运行机制**
10. IIS 承载方式由我方按**更安全**的方式选型
11. `ARR / URL Rewrite` 的离线安装包可以由我方随交付包一起提供

## 当前需求边界

后续兼容版重构默认按 [需求边界说明.md](./需求边界说明.md) 执行：

1. 主需求：给现有官方 APP 套网关
2. 次需求：浏览器和 APP 都走统一认证
3. 非当前主需求：开放给第三方 APP 的自定义接入协议

因此，仓库里保留的 `AppKey / AppSecret / HMAC` 这套能力，当前应视为可选增强项，而不是兼容版第一优先级的验收主线。

## 当前结论

到目前为止，**技术栈层面已经足够开工**，不再存在会卡住重构路线的架构级问题。

我这边现在可以按下面的方向继续推进：

1. 网关作为**独立站点**实现，不要求与 ERP 原页面框架一致。
2. 接口层按 **Web API2** 作为优先实现路线。
3. 反向代理按 **IIS ARR + URL Rewrite** 落地，并随交付包提供离线安装材料。
4. 网关自有数据优先落 **SQLite**，降低客户部署成本。
5. 安全策略、站点隔离方式、后台入口组织方式由我方按更安全的方案落地。

## 仍需公司提供的联调资料

这部分已经不是“技术栈确认”，而是后续把**现有官方 APP**真正接到网关前时需要核对的联调资料：

1. 官方 APP 实际连接的企业站点地址 / 企业号 / 服务器地址填写规则
2. 登录前初始化接口清单，例如 `sys.ashx`、`tenant_name`、`fileversion` 是否固定
3. 主登录接口路径与关键入参字段
4. 登录后核心会话字段 `userToken / SessionKey` 的携带方式
5. 需要优先覆盖的官方 APP 版本范围（安卓 / 苹果 / 新旧版）
